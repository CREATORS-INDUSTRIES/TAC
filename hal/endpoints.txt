hal — endpoints (http://172.20.10.6:8080)

ESTADO

  curl "http://172.20.10.6:8080/state"
    posicion + motor (direction, speed, busy) + t. "/" igual.

  curl "http://172.20.10.6:8080/position"
    solo posicion 0.0-1.0.

MOVIMIENTO

  curl "http://172.20.10.6:8080/move?to=0"
    bucle cerrado hasta to (0.0-1.0). Bloquea hasta llegar o timeout. 409 si motor ocupado.

  curl "http://172.20.10.6:8080/drive?dir=forward&speed=0.5&ms=200"
    empuje crudo, se para solo a los ms.
    dir = forward|backward (def forward), speed def 0.5, ms def 200 (clamp 1-1000).
    409 si ocupado.

  curl "http://172.20.10.6:8080/stop"
    para motor, cancela auto-stop de drive.

PANTALLA

  curl -X POST --data-binary @logo.svg "http://172.20.10.6:8080/screen?threshold=128&dither=false&invert=false"
    body = SVG, lo pinta centrado. Query opcional (valores = defaults).
    usar --data-binary, no -d. Max 64KB. 503 sin pantalla, 400 si SVG invalido.

MODO SERIE

  controller --mode serial [--device /dev/serial0] [--baud 115200]
    misma API sobre puerto serie (8N1, sin control de flujo). Defecto sigue siendo --mode http.
    al arranque: ExecStart=/usr/local/bin/tac-firmware /usr/local/bin/controller --mode serial
    en serie tac-firmware se salta netplan/IP/gesto del fader: logo y controller directo.

  peticion: una linea "GET <ruta>"            ej. GET /move?to=0.3
            o "POST <ruta> <len>" + len bytes  ej. POST /screen?invert=true 1834  y luego el SVG
  respuesta: una linea "<codigo> <json>"      ej. 200 {"position":0.31,...}

  picocom -b 115200 --omap crlf --echo /dev/ttyUSB0    y teclear GET /state

  solo por serie (no existen en HTTP):
  POST /update?name=controller|tac-firmware|service&crc=<crc32> <len>
    reemplaza el fichero instalado (escribe .new y renombra). 400 si el crc no cuadra.
  GET /restart
    daemon-reload y sale; systemd relanza tac-firmware.
  GET /console
    cede el puerto a un login (agetty). Al salir de la sesion (exit/Ctrl-D) vuelve el firmware.
    desde esa shell no hagas systemctl restart tac-firmware: matas tu propia sesion.

  deploy por serie: ./tac-firmware/deploy.sh /dev/cu.usbserial-XXXX    (BAUD=... si no es 115200)

EVENTOS (solo serie)

  GET /subscribe?events=manual,motor,position,screen&hz=100
    sin events = todos. hz 1-200 (def 100) = maximo de eventos position por segundo.
    solo se emite cuando algo cambia; con el fader quieto no sale nada.
  GET /unsubscribe
    apagados al arrancar y cuando el otro extremo cuelga.

  lineas de evento empiezan por "@ ", las respuestas por "<codigo> ":
  @ {"event":"manual","phase":"start","position":0.30,"t":...}       mano mueve el fader con motor parado
  @ {"event":"manual","phase":"end","position":0.42,"t":...}         150ms quieto
  @ {"event":"position","position":0.41,"source":"manual|motor","t":...}
  @ {"event":"motor","phase":"start","cmd":"move","target":0.8,"t":...}
  @ {"event":"motor","phase":"start","cmd":"drive","direction":"forward","speed":0.5,"ms":200,"t":...}
  @ {"event":"motor","phase":"end","position":0.80,"t":...}
  @ {"event":"screen","w":128,"h":64,"bitmap":"<base64>","t":...}    tras cada POST /screen ok
    bitmap = pantalla entera, 1 bit/pixel, filas de arriba abajo, 16 bytes/fila, MSB = pixel izquierdo
